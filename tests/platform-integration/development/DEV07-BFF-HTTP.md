# DEV-07 native estate BFF HTTP qualification

Run `python3 -B tests/platform-integration/development/buyer_bff.py` inside the
existing integration devcontainer with `BAOBAB_ENVIRONMENT=development` and the
same transient package-read variables used by the CMS source builder. The
dedicated Actions job supplies these only for a trusted repository candidate.

This supplemental profile builds the pinned ZuriBeans standalone Next server and
the compiled native Medusa server. It uses actual TLS Redis, native Kratos login
and WhoAmI, Hydra code/PKCE/consent/token/introspection, and the real CP owner
fixture, Principal resolution, estate binding and Organisation/Market authority.
It never signs a token, writes CP SQL or promotes a Medusa key into buyer access.
The native publishable Store key satisfies Medusa's router only; IAM/CP and
current native membership still decide every buyer-context operation.

The driver follows the authorization URL generated by the real BFF. The BFF
alone holds the verifier, nonce, human access token and encrypted session. The
synthetic IAM owner completes actual Kratos/Hydra challenges, then the driver
visits the actual BFF callback with its original opaque browser binding. The
introspection relay uses real Hydra readback and permits this BFF to inspect its
own client only. The BFF receives no global introspection or issuer-admin secret.

Eight supplemental observations cover the native Next/IAM session, independently
CP-matched Trade HTTP context, CSRF refusal, foreign Organisation refusal,
membership suspension, custody outage and recovery, issuer consent revocation
before advertised session expiry, and native fixture deletion/readback. Pausing
Redis proves dependency failure without discarding the session, and recovery
must succeed again. Revocation is scoped to the run-owned human/BFF grant and
independently read back at the issuer; no token is extracted from custody.

The profile has separate base/owner locks. The existing eight-case direct-handler
qualifier, all historical receipts and every original INT-05 scenario remain
unchanged. Source tests are labelled synthetic and cannot qualify this runtime.

Every source/image is tied to the private run. Actual container image identity,
non-root estate execution, no host ports and the isolated internal network are
read back. Configuration hashes are rechecked before the native CLI and probes.
Native and issuer cleanup plus independent CP binding revocation are attempted;
host teardown runs even when leases or providers fail. The common watchdog and
separate host recovery remain mandatory. Only sanitized completed receipts and
their hashes leave the private run; OAuth codes/cookies, tokens, credentials and
provider bodies do not.

The private component receipt always has `bff_http_qualified=false` because the
driver cannot witness host disposal. Only the final Infrastructure wrapper may
set it true after all observations, independent owner cleanup, runtime identity
and verified host teardown. This qualifies the source HTTP component, not the
complete browser account UI or INT-05 commercial journey. Provider, protected
and production acceptance remain false. It activates no purchasing operation,
RFQ/quotation lifecycle or native buyer commitment enforcement gate.

## Governed buyer transaction trace

Run the buyer commitment against the development deployment with the approved
Trade price issuer and a disposable governed cart. Keep the existing
buyer-context component run and synthetic origin refusal as separate evidence.
For the connected run, use one private OTLP collector for ZuriBeans, Trade,
CP, the IAM issuer, the publisher and ERP. Start the browser request without
an incoming trace header so the confidential ZuriBeans route owns the root.

Set `BAOBAB_DEV11_CP_OTLP_TRACES_ENDPOINT` to the collector's HTTP
`/v1/traces` URL. For the pinned Hydra issuer, set `tracing.provider` to
`otel`, `tracing.service_name` to `baobab-iam`, and
`tracing.providers.otlp.server_url` to the private collector's host and port.
Set `tracing.providers.otlp.insecure` only if the disposable collector uses
HTTP. Preserve the W3C trace header through the private introspection relay.

Pass the independently read Trade receipt to `dev11_exported_trace.py` using
`--native-origin`. Use the trace ID from that receipt with `--trace-id`.
The observer reads Jaeger directly and matches the exact outbox span, event ID,
BFF root, CP decisions, IAM introspection edge, confirmed publication, ERP
admission, worker and its native engine call. Retain the independent iDempiere
and CP database readbacks alongside the export. The exported graph alone
grants neither business-effect qualification nor L4-OPS-01 acceptance.

### Submit the disposable checkout through the existing probe

In the active private buyer BFF run, after login and after Trade records the
approved fixture price and spend hold, write `bff-checkout-selection.json` in
the private probe directory with the exact `cart_id`, `country_code` and a
fresh `idempotency_key`. Invoke the existing probe with the `checkout` action
(`python /buyer_bff_probe.py checkout` in the probe container). It sends a
wrong-CSRF request before the first commit, then requires the same order on
an authorised retry with the original key. The resulting
`bff-checkout-observation.json` contains private correlation material and
stays inside the run.

On a separate read-only connection to the run's Trade PostgreSQL database,
pass the observed `order_id` and `idempotency_key` to Trade's
`dev11_native_business_origin.py --order-id ... --idempotency-key ... --output ...`.
The observer requires exactly one matching canonical event and proves the
same transaction through the existing native readback. Retain the original
event ID from that receipt for the publisher. The checkout action is
operator-invoked on a provisioned fixture.
